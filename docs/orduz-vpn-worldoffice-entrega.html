Estado general: recursos Azure creados y conexión VPN configurada del lado Azure. El túnel aparece NotConnected hasta que el equipo FortiGate configure su extremo y use la PSK acordada.

1. Alcance de la entrega

Se dejó aprovisionada la infraestructura base en Azure para alojar el aplicativo World Office y establecer una VPN Site-to-Site contra el FortiGate del cliente.

  • Máquina virtual Windows Server para World Office, sin IP pública.
  • Red virtual y subredes requeridas para aplicación y VPN Gateway.
  • Azure VPN Gateway route-based compatible con IKEv2.
  • Conexión Site-to-Site hacia la IP pública FortiGate del cliente.
  • Backup habilitado para la VM mediante Recovery Services Vault.

7. Validación esperada

  1. Configurar en FortiGate el túnel hacia el peer público Azure 172.193.77.244.
  2. Aplicar la PSK entregada por canal seguro y los parámetros IPSec/IKE indicados en este documento.
  3. Configurar rutas entre la red local 192.168.1.0/24 y la red Azure 10.80.0.0/16.
  4. Verificar que el túnel pase a estado conectado del lado FortiGate y en Azure.
  5. Probar conectividad desde la red cliente hacia 10.80.1.10.
  6. Validar acceso RDP o los puertos requeridos por World Office según el alcance operativo definido.

8. Pendientes y confirmaciones

  • Confirmar si la LAN del cliente es exactamente 192.168.1.0/24 o si deben agregarse más redes.
  • Confirmar si el FortiGate quedará en route-based con IPsec interface/VTI.
  • Entregar PSK por canal seguro al administrador FortiGate.
  • Definir puertos finales de World Office, SQL Server y acceso administrativo.
  • Realizar prueba conjunta durante ventana de implementación.
